1. 项目、研究编号与记录

后台按“项目 → 编码患者 → 基线、随访及扩展记录”组织数据。一个项目具有独立的 project_id、中心代码 center_code 和模块 module。多中心可以各建独立项目，按批准范围分别授权后汇总；当前没有自动覆盖所有中心的组织权限。

  • 研究对象身份键是 project_id + center_code + patient_code；每条记录另有原始 id。同一编号在不同中心或项目中不应被当作同一个人。
  • 0001、1 和文字编号须原样保留。不要在电子表格中自动转为数字，不因合并方便而改写项目或记录 ID。
  • 编号与姓名的映射由来源机构按批准方式保管，不上传到登记系统。一个患者在同一项目内保留一条基线，后续随访按日期新增。

2. 成员权限与交接

  1. 同行注册自己的邮箱账号并完成邮箱验证，不能共用负责人密码。
  2. 负责人选择项目，在项目成员区输入同行邮箱，选择 editor、analyst 或 viewer。此操作添加已有验证账号，不是自动发送邀请邮件，也不能授予 owner。
  3. 受邀同行重新加载项目列表，核对项目名、中心和角色。负责人按分工调整角色，离组时移除成员。原 editor 被移除或降为 analyst/viewer 时，系统会在操作确认后撤销该项目所有有效随访链接；需要继续随访的，由 owner/editor 重新发放。

3. 研究授权与隐私

使用真实记录前，机构与项目负责人应确认研究方案、适用的伦理审批与知情同意/豁免、数据用途、字段范围、成员与导出接收方。系统账号、冻结版本或质控通过不能代替上述确认。

医疗健康属于敏感个人信息；研究编号替换姓名通常是去标识化，不能据此认定匿名化。编码后的记录仍可能与个人关联，按敏感个人信息管理。参见《个人信息保护法》第28、73条。

  • 不要输入姓名、电话、身份证、病案号、完整住址或编号映射，也不要把含这些内容的报告全文粘贴进备注。
  • 系统对部分常见身份信息模式有提示或阻断，但不能识别所有姓名、变体或组合识别风险；提交前仍需人工核对。
  • 阿里云网页托管不能证明数据库、认证、日志、备份均在境内。技术与机构负责人应核对实际服务位置、数据流和授权文件，不能按前端域名作结论。
  • 误录或误分享时，停止进一步传播并联系项目与机构数据负责人处置。不要为“修复”而自行大批删除记录或销毁留痕。见隐私政策、安全说明。

4. 首次准备：负责人完成后交接给同行

  1. 在登录页用邮箱和密码登录。负责人新建项目，填写清晰名称、独立中心代码和模块；同一个中心的新研究也应有独立项目身份。
  2. 按方案确认基线日期定义、访视窗口、肌酐/蛋白尿单位、病理与事件定义，以及哪些字段允许缺失。把数据字典版本交给所有录入人员。
  3. 按权限表添加同行，确认各自项目可见性。先用模拟记录演练录入、纠错和一次冻结导出，再开始批准范围内的正式采集。
  4. 确认数据保管、支持联系人、离组处理和备份恢复安排。新版本冻结功能保留导出内容，不替代日常备份与恢复演练。

账号与项目准备遇到问题

忘记密码用登录页“忘记密码”发送重置邮件，核对邮箱及垃圾邮件。添加成员失败先核对邮箱验证、是否已在项目中、角色及频率限制。不要反复尝试枚举他人邮箱；仍失败由负责人联系支持。

5. 日常录入与核对流程

  1. 先选项目：看当前项目名称、中心和角色，再打开“患者与基线”。研究编号搜索能找到已有基线时，进入原记录，不重复建立。
  2. 填写基线：按来源填写研究编号、性别、出生年、真实基线日期及已获得指标。基线肌酐按 μmol/L；UPCR 选报告单位后核对保存值。基线日期暂缺时可保留缺失，但脚本不能建立年度窗口或基线变化。
  3. 病理和分组：只转录已有报告或批准分配结果。没有报告留空，不把未知病理评分填0；随机分组字段不提供自动随机化或分配隐藏。
  4. 增加随访：按随访链接流程核对研究编号、随访日期、血压、肌酐、UPCR及原单位。缺少必填结果时先联系研究人员，不填0以通过提交。
  5. 核对保存：看到成功回执后，在患者列表“随访记录”中检查日期、数值及单位。历史页有分页，近期随访页面不是完整数据集。
  6. 发现错误：用“基线更正”或“随访记录”中的“核对 / 更正”，核对变更预览、填写原因后保存。研究编号不能在更正窗改写；编号错误先交由负责人核查归属。

6. 随访链接：发放、提交、撤销

随访链接是一项访问凭证。收到完整链接的人无需后台登录即可进入对应研究编号的填报页，并可能看到相应研究记录；请仅交给授权填写人，不发到公开群、公开文档或截图中。

  1. owner/editor 在“随访链接”选择研究编号、最短适用有效期和是否单次使用。当前默认有效期30天、单次使用；按任务调整并核对。
  2. 点击“生成随访链接”，复制页面生成的完整链接，不自行拼接或删去随机码。填写人打开后先核对项目与研究编号，不匹配就停止填写。
  3. 先选择报告单位，再核对页面换算值并提交。成功后保留回执；单次链接已用、过期或撤销后不能继续提交。若仍需下一次随访，由研究人员重新发放。
  4. 重复使用链接也须有明确任务和有效期。任何泄露或不再需要的链接，由 owner/editor 在链接列表撤销；项目到期仍应及时撤销泄露凭证。

提交超时先查看提示、重试同一次操作或重新验证链接，再核对回执/历史；不要立即创建新的相同记录。历史读取失败不代表提交未成功。切换项目、账号或链接后重新核对上下文。

8. 化验及扩展记录

先选患者，再选检验项目代码、采样/检验日期、原始数值与原单位。核对标准值提示；修改历史记录时用“核对 / 更正”并说明来源。新旧原值/单位必须是同一组，不能把一个来源的数值与另一个来源的单位拼接。

CD19百分比不能直接当作细胞绝对计数；病毒 copies/mL 与 IU/mL 不能在缺少已验证换算关系时按1:1互换。无法换算或原值与标准值矛盾时，记录保留并交团队核实，相关结果不进入分析。

用药按已有记录填写名称/分类、剂量、途径、频次和日期；事件填写类型、日期、来源与确认状态。系统登记不产生用药建议，人工事件也需按研究方案裁定。

病理、LOINC、HGVS 与其他专业字段

病理评分照报告转录；LOINC须匹配实际项目、样本、方法与单位；基因字段保留报告中的基因、HGVS、转录本、合子状态及来源。不要为填满表格编造专业代码。当前分析脚本不执行基因变异解释，也不会因字段齐全自动生成遗传诊断或专病风险分层。

9. CSV 批量导入

  1. 选择正确项目和“患者基线”或“随访记录”，点击“下载模板 CSV”。当前只提供这两类批量导入，不把其他长表直接套入模板。
  2. 每批最多500行、文件不超过2MB。保留表头，研究编号按文本保存。基线填写已核实的 UPCR 单位列，或在页面明确选择该批未标注记录的单位；混合单位文件应逐行标注。
  3. 确认肌酐列为 μmol/L、随访 UPCR 为 mg/g，勾选单位确认后选择文件，查看预览、错误行与拟变更。先修正重复编号、必填值、日期及单位问题。
  4. 点击“确认导入”。服务器整批校验；校验失败不会只导入前半批。网络中断则先查看反馈，在原页面重试同一批次，再核对患者/随访数量，不另建一份重复批次。
  5. 已有基线仅按本次明确提供字段处理，空白不用于随意清除已有内容；需要清空或纠正原记录时用更正功能并留原因。

导入预览和服务器校验是质量控制的一部分，不能替代授权、单位核实或对原始病历的人工核对。无法确认来源的值不要通过填假单位或假0强行导入。

10. 质控与更正闭环

  1. 在“待办与质控”刷新列表，按研究编号和问题定位。看到“读取失败”先解决读取问题，不能当作零问题。
  2. 点击“核对原记录”，对照报告调整可更正字段，填写具体原因，确认前后值后保存。
  3. 刷新列表确认重新校验结果。不能通过直接把问题标成已解决来代替数据更正。
  4. 如果团队核实后决定保留异常原值，选择“接受不修复”并写理由。该状态与“已修正”分别统计，原数据仍保持原样。

QC没有未处理项目不代表数据已完整、所有隐私风险已消除或临床终点已成立。本地分析还会另查身份、时间、单位与公式来源，并输出 qc_issues.csv 和 qc_report.xlsx。

11. 冻结数据、下载分析包、复核结果

11.1 选择导出方式

owner/analyst 可单独下载基线、随访等 CSV 作核对；各次下载可能对应不同时间。需要同一数据版本时，点击“冻结并导出完整分析包”或“导出分析脚本包（ZIP）”，两个入口均使用一次数据库一致性读取。

“冻结当前数据版本”只保存当前版本。版本列表中“已冻结数据”可用“下载已冻结JSON”重下相同内容及校验值；“旧元数据记录”仅有说明/数量，不能恢复历史数据。冻结不会锁住后续录入，也不等于备份恢复。

11.3 校验与留存

export_manifest.json 记录源内容 source_content_sha256 及各文件 SHA-256。先保留未经修改的 ZIP 与清单；客户端在读取冻结内容时核对哈希，校验失败会停止下载。重下同一冻结版本的 JSON 应有相同哈希，重新生成的 ZIP 可能因导出时间或脚本版本不同而不同。

如需人工核对，在解压后的包根目录运行以下一条命令，将输出与清单中 source_content_sha256 比较：

python -c "import hashlib,pathlib; print(hashlib.sha256(pathlib.Path('research_data.json').read_bytes()).hexdigest())"

SHA-256 用于发现内容变化，不证明研究结论正确或数据已匿名化。只在获准的协作范围与环境内分享包，不把真实记录传到公开仓库或公开咨询工具。

11.4 本地运行

使用 Python 3.11 或3.12，在含 analysis/ 的包根目录打开终端，先创建独立环境：

python -m venv .venv

Windows 命令提示符运行 .venv\Scripts\activate；macOS/Linux 运行 source .venv/bin/activate。激活后执行：

python -m pip install -r analysis/requirements.txt
python analysis/run_analysis.py

仅在看到 DESCRIPTIVE_REVIEW_OK 后，把新 analysis/outputs/run-时间/ 目录视为本次结果。ANALYSIS_FAILED 表示本次失败，应先解决输入问题；不把上次结果冒充本次输出。

  • table1_baseline.xlsx：描述统计与各指标可用人数。
  • outcomes_12m.csv：在基线后270–450天中选离365天最近的一整条访视；无记录为不可评估，不拼接不同访视或补0。
  • candidates_egfr_decline.csv、candidates_igan_proteinuria.csv：数值阈值候选，不代表持续性、临床裁定或方案确认的终点。
  • manual_events_review.csv：逐条保留人工事件，检查确认状态及时间；明确确认且日期在基线之后才标为 confirmed_in_followup。
  • egfr_slope_per_patient.csv 与趋势图：描述性趋势；斜率至少需要两个不同日期，同日重复值先求均值。
  • RUN_LOG.json、METHODS_ACTUAL_EN.md、MODEL_STATUS.json：本次输入与输出哈希、人数、版本、实际方法和未执行功能。模板文件本身不是已经运行的 Methods。
明确未执行：KFRE 风险计算、LME 队列推断、置信区间、生存/因果分析、自动缓解或持续性临床终点判定。当前不输出这些风险数值或模型结果。专业团队须另行制定、验证并记录适用的统计分析计划；不能把数值候选直接改名为已确认终点。

11.5 多中心合并

各中心先按批准范围导出，把六张核心机器 CSV 分别放入 centers/A/、centers/B/，保留各自原始项目、中心及记录身份。不要混入 Excel 安全副本或偷偷改写 ID：

python analysis/merge_centers.py --dirs centers/A centers/B --out analysis/merged-data --qc merge_qc.xlsx
python analysis/run_analysis.py --data analysis/merged-data

只有出现 MERGE_OK 才运行第二条。相同记录 ID 且内容完全一致可去重；同 ID 内容不同或同患者多条冲突基线会阻止合并。不同日期/不同 ID 的重复事件会保留。QC文件必须位于输入和合并输出目录之外；重跑使用新的空输出目录。核对 RUN_LOG 的 input_dir、人数与输入哈希确实对应合并数据。两张移植扩展表不在此核心合并脚本范围内，不能宣称已汇总它们。

12. 一次模拟演练
