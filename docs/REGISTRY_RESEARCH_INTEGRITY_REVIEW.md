# 实际版本的研究分析审查记录

审查版本：`742b279f343c6cbc8cd0472f286dad645270fe3e`。仅审查源码和合成数据机制，未读取生产数据库，也未确认线上数据是否受影响。以下事项需在正式多中心研究分析前修复和验证；首页与合作页改版不包含这些计算改动。

## 1. 基线 UPCR 的单位约定不一致

`site/staff.html` 的基线输入标签允许 mg/g 或 g/g，却没有对应单位选择。`site/staff.js` 的 `createPatientBaseline()` 直接保存数值，导出字典则将 `baseline_upcr` 标为 mg/g。患者随访端 `site/patient.js` 对 g/g 输入会乘以 1000。

因此，相同单位选择习惯可能使基线 2 g/g 保存为 2，而随访 1 g/g 保存为 1000，影响后续比值或变化量。应增加明确的基线单位选择并统一存储；历史无单位记录必须核实来源，不能根据数值大小猜测后批量换算。

## 2. 按列取首个非空值会拼接不同访视

`site/assets/template/run_analysis.py` 中，首次访视和最接近 365 天的访视使用 `groupby(...).first()`。该方法逐列选择首个非空值，不能保证各项指标来自同一条访视。

例如，一次访视仅有 UPCR，下一次仅有 eGFR，结果可被拼成第一天同时存在两项指标。修复应保留访视 ID，按照预定窗口和并列规则选取完整的一行，保留该行缺失值，并对无法唯一选择的记录出具 QC 提示。

## 3. 跨中心与跨项目身份处理仍不完整

实际版本多数关联已使用 `center_code + patient_code`，不能沿用旧仓库中“仅按患者编号关联”的笼统结论。但是，用药汇总仍有仅按 `patient_code.nunique()` 计数的情况：两个中心都有 P001 时可能被算作一个人。

分析及合并脚本读取 CSV 时还会推断编号类型，可能将 `001` 与 `1` 视为同一个数值。导出没有完整保留项目和记录 ID；`merge_centers.py` 按部分键执行 `keep="first"`，可能静默丢弃同日不同访视、重复事件或不同项目中的同编号记录。

修复须从导出到合并和分析保留字符串身份字段、项目和记录 ID，并用完整的患者键计数。合并前须核对研究方案与项目映射；完全相同的重复记录可明确处理，内容冲突不能自动保留第一条后继续。

## 4. KFRE 与检验单位需要单独验证

当前分析代码用 UPCR 作为 uACR 的替代输入，并存在按队列中位数猜测部分检验单位的逻辑。这是源码行为记录，不是对该做法或公式系数的医学认可。本次没有核验 KFRE 系数、适用人群和校准；正式使用前应按原始模型要求核对变量、单位、缺失处理和验证范围。

## 与旧仓库草稿的关系

实际 `site/staff.js` 生成论文包时读取 `/assets/template/run_analysis.py` 等文件。之前 `followup-registry` 仓库草稿修改的 `analysis/run_analysis.py` 不是这个部署路径，不能视为本版本已经修复，也不能直接覆盖使用。后续应在本仓库另建分析修复变更，并使用跨中心同编号、前导零、同日多访视、缺失值和单位转换等合成用例验证。
